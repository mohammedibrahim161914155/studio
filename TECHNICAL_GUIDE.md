## 1. Technology Stack

-   **Framework:** Next.js (App Router)
-   **Language:** TypeScript
-   **UI:** React, Tailwind CSS, shadcn/ui
-   **P2P Connection:** WebRTC (via `simple-peer` library)
-   **State Management:** Zustand
-   **Offline Storage:** IndexedDB (via `idb` library)
-   **Cryptography:** Web Crypto API

---

## 2. Project Structure

The codebase is organized with a clear separation of concerns.

-   `src/app/`: Contains the pages and routing for the Next.js App Router.
-   `src/components/` & `src/ui/`: Reusable React components. `ui` contains the base shadcn/ui components, while `components` contains application-specific components.
-   `src/core/`: Houses the core application logic and state management stores.
    -   `transfer.ts`: Manages the state of the file transfer queue.
    -   `peer-manager.ts`: Manages the list of known peers and their trust status. Includes `useKeyStore` for cryptographic identity.
    -   `transfer-log.ts`: Manages the persistent history of transfers.
    -   `benchmark.ts`: Manages the state and logic for performance benchmarking.
    -   `db.ts`: A lightweight wrapper around IndexedDB for storing and retrieving file chunks.
-   `src/connection/`: Contains the WebRTC connection logic.
    -   `peer.ts`: The main Zustand store (`usePeerStore`) for managing the `simple-peer` instance, connection status, and the P2P messaging protocol.
-   `src/hooks/`: Custom React hooks, such as `use-toast`.

## 3. Core Concepts

### State Management (Zustand)

Zustand is used for global state management due to its simplicity and performance. State is decoupled into several focused stores:

-   `useTransferStore`: Manages the list of files in the transfer queue, their progress, and status.
-   `usePeerManagerStore`: Manages the list of saved peers, their names, and their trusted status.
-   `useKeyStore`: Manages the device's own cryptographic key pair (ECDSA P-256) used for the security handshake. Keys are generated once and persisted.
-   `usePeerStore`: Manages the active WebRTC peer connection, its status (`connecting`, `connected`, `error`), and provides the core `send` and `signal` methods.
-   `useLogStore`: Manages the persistent transfer history.
-   `useBenchmarkStore`: Manages the state for the performance benchmark feature.

All stores that require persistence (e.g., peers, logs, keys) use `zustand/middleware/persist` to save state to `localStorage`.

### Connection Layer (WebRTC)

WebRTC connectivity is abstracted by the `simple-peer` library. The `usePeerStore` acts as a facade around the `simple-peer` instance.

-   **Signaling:** The application uses "manual signaling." Connection offers and answers (SDP) are generated by `simple-peer` and must be transmitted between users out-of-band (e.g., via QR code, text copy/paste, or a shareable link). This avoids the need for a signaling server, making the architecture truly serverless.
-   **Data Channel:** All communication, including file chunks and control messages, occurs over a reliable, ordered SCTP data channel provided by WebRTC.

### P2P Messaging Protocol

A custom JSON-based messaging protocol is defined in `src/connection/peer.ts` under the `PeerMessage` type. This protocol runs on top of the WebRTC data channel and allows for structured communication between peers. Key message types include:
-   `metadata`: Sent before a file transfer to inform the receiver of the file's name, size, type, and checksum.
-   `chunk`: A single chunk of a file.
-   `resume-request`: Sent by a receiver to request resuming a transfer from a specific point.
-   `key-exchange`: Used to securely swap public keys upon first connection.
-   `challenge-request` / `challenge-response`: Used for the cryptographic handshake with trusted devices.
-   `benchmark-*`: A set of messages to coordinate the performance benchmark test.

### Security Model

Security is a core pillar of the application, implemented via a cryptographic trust system.

1.  **Key Generation:** On first launch, `useKeyStore` generates a unique ECDSA P-256 key pair for the device. The public key serves as the device's shareable identity, while the private key is securely stored and used for signing.
2.  **Key Exchange:** When two peers connect for the first time, they automatically exchange their public keys via the `key-exchange` message.
3.  **Establishing Trust:** When a user "trusts" a peer, the app saves that peer's public key in the `usePeerManagerStore`.
4.  **Cryptographic Handshake:** On subsequent connections to a trusted peer, the following challenge-response verification occurs automatically:
    -   The initiator sends a `challenge-request` containing a randomly generated nonce.
    -   The receiver signs the nonce with its private key and sends it back in a `challenge-response`.
    -   The initiator uses the stored public key to verify the signature. If verification fails, the connection is immediately terminated.

This process ensures that auto-reconnections are secure and resistant to man-in-the-middle (MITM) attacks.

### File Transfer & Resume

-   **Chunking:** Files are split into fixed-size chunks (128KB) before sending. This ensures stable performance and allows for progress tracking and resumption.
-   **Parallel Sending:** To maximize throughput, the sender uses a pipeline of asynchronous workers to send multiple chunks concurrently. The `PARALLEL_CHUNKS` constant in `header.tsx` controls the level of parallelism. This saturates the data channel's send buffer without overwhelming it.
-   **Checksum:** Before sending, a SHA-256 checksum of the entire file is calculated. This is sent with the `metadata`. After the receiver assembles all chunks, it calculates its own checksum and verifies it against the sender's. If they don't match, the transfer is considered corrupt, and a retry is requested.
-   **Cross-Session Resume:** The receiver stores incoming chunks in an IndexedDB database (`src/core/db.ts`). If a connection drops, the partial data remains. On reconnection, the receiver calculates which chunks it has, sends a `resume-request` to the sender, and the transfer continues from the last successful chunk.

### Performance Benchmarking

The benchmark feature (`src/app/benchmark/page.tsx` and `src/core/benchmark.ts`) is designed to measure the raw network performance of the WebRTC connection.

-   It transfers 100MB of data generated purely in-memory to eliminate disk I/O from the measurement.
-   It measures the total time taken and calculates the throughput in **Mbps (Megabits per second)**.
-   Results are stored persistently, allowing for performance tracking across different networks or after code optimizations.
